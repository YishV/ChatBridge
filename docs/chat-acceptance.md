## 参与规则

原生 `@` 直接回答。其他文本在频率允许时由模型判断是否接话；直接称呼机器人并提问或延续机器人上一条话题时优先接话，群友之间的普通闲聊可以沉默。自然决定使用 JSON 结构化输出，无效内容按沉默处理。

默认明确 `@` 冷却 5 秒、每群每小时最多 60 次模型调用。普通消息在最后一次发言约 5 秒后合并判断。每群上下文最多 20 条、10 分钟，仅内存保存；只有确认已发送的助手回复进入上下文。后台保持运行才能继续聊天，重启不补答历史。

## 自然接话与人设修复复验

用户反馈连续消息未获接话后，脱敏计数显示最后两次分别触发旧的 30 秒冷却与一次模型异常；旧日志不足以还原该次异常的具体 HTTP 状态或完成原因。经用户确认，现改为约 5 秒的连续发言合并，模型故障会记录固定分类代码，避免把故障混同于模型沉默。

更新后用户确认收到接话；后台记录先 `deferred` 等待，在没有新输入的轮询中完成 `naturalEvaluated`，取得一次 `confirmed` 发出回执，未出现模型错误或未确认发送。连续两条合并上下文的行为另有可控时钟回归覆盖。

独立人设文件 `config/persona.md` 已接入，保存后下一次请求读取；文件热更新、空/缺失/编码错误/超限、规则附加均通过测试。多群到期批次采用逐群生成后立即投递，首群致命错误阻止后续群推理。此轮完整回归 89 项通过。

## 拍一拍接入复验

原先网关仅接收文本，原生拍一拍被过滤。现已单独解析原生拍一拍事件，核对发起人、群和目标，只接受群友拍当前机器人；拍别人、自拍和手打文本不触发此分支。事件使用固定互动描述，不将拍一拍后缀传作提示词，也不伪装成原生 `@`。

用户确认收到按人设生成的文字回应；只读核对近期原生拍一拍与其稳定消息标识，匹配到两次 `confirmed` 投递及服务器消息 ID。较早、修复前的事件没有投递记录，不补发历史。

完整离线回归 105 项通过，包含严格 XML/压缩边界、目标校验、直接回应、限流/暂停/去重及取消自然待处理批次。审查另发现拍一拍初始服务器编号为 0 时会推进游标，已纳入等待逻辑，并以先失败后通过的两轮读取回归验证。更新后的持续后台已就绪，标准错误日志为空。

拍一拍仅触发文字回复，不执行拍回；沿用默认 5 秒冷却与每群每小时 60 次模型配额。连续密集拍动可能被限流。

## 成员区分与模型错误修复复验

收到自然接话 `model_response_invalid` 反馈后，确认原实现把响应 JSON 错误、结构异常和空内容合并显示，缺少进一步诊断，历史返回正文没有留存，无法断定该次具体形态。现已区分这些情况，默认单次超时 45 秒、输出 1200 token，可恢复失败最多重试一次，重试占用群配额；失败只留安全错误码与尝试次数，不会自动重发微信消息。

读取层已能区分授权群三位实际成员，均可读到微信昵称。新增稳定 API 成员名、当前说话人及历史助手回复归属，昵称相同不合并，改昵称和改人设不更换标识。联系人查询只取有效消息发送人的微信昵称，不取个人备注。生产标识密钥在本机保留，短期聊天内容仍不持久化。

完整回归 203 项通过，真实 DeepSeek 的两个虚构成员测试中，名字和偏好分别匹配；这不是实际微信群双成员验收。审查发现的 HTTP 协议异常漏接已修复。新版后台已启动；用户决定先使用、出现问题再反馈，本轮不再要求现场双成员验收，后续错误率继续观察。具体方案见 [修复记录](plans/2026-10-20-chat-reliability-and-members.md)。

## 自然参与空响应修复

用户反馈自然接话经常以 `model_response_empty` 结束，且重试后仍失败。用真实 `deepseek-flash` 和当前人设做合成探测发现：JSON Output 请求在该长人设下稳定返回纯空白（6/6 次，`finish_reason=stop`），普通文本请求正常，最小 JSON 提示也能正常返回。问题不是偶发的服务波动，而是 JSON Output 与当前长人设组合下的稳定空内容；DeepSeek 文档也提示该模式可能返回空内容。原有的一次重试只是再次得到空白并多消耗配额。

自然参与、`@` 配图和拍一拍配图现已改用强制的 `decide_reply` 工具调用：`reply` 填正文，空字符串表示沉默，`reply:null` 归一为沉默。空回复不再记为 `model_response_empty`；工具参数损坏、缺失或截断仍保留安全错误码并最多重试一次。真实探测中合成自然消息可正常接话或明确沉默，`@` 消息可回复并选图，未向微信群发送消息。详见 [空响应修复记录](plans/2026-10-20-decision-tool-empty-json.md)。

## 聊天记录持久化

用户已确认持久化范围。现有 SQLite 新增 `chat_history`，授权群新发言与认领状态同事务，机器人回复仅在服务器回执确认时与投递状态同事务保存。每群启动恢复最近 50 条，可配置 1～200；恢复后不再按十分钟过期，完整存档默认保留。历史仅供上下文参考，不触发补发或恢复待处理批次，成员标识和回复对象沿用，人设文件不变。

完整回归 226 项及独立审查通过。使用虚构数据完成跨连接与独立 CLI 的重启恢复验证，未请求真实模型或向微信发送验收消息。业务库已备份并创建新表，完整性检查为 ok；迁移时没有既有聊天存档。用户自行启动，新版启用后开始保存，旧版未存下来的聊天不回填。详见 [持久化记录](plans/2026-10-20-persistent-chat-history.md)。

## 场景表情包

场景表情包按独立计划接入：公开图库索引同步、本机静态 GIF 缓存、模型在同一次请求返回文字与已注册 `meme_id`、文字确认后最多发送一张、每群 60 秒冷却和最近 5 张避重、图片回执确认及失败不重发。图片准备或发送失败只保留已发送文字；暂停/撤群同样阻止配图。只支持静态素材，动图和微信原生收藏表情未接入。

现场发现大尺寸 GIF 会被微信当文件卡片发送。微信规则是宽超过 1000 像素或文件超过 10 MB 时按文件发送；原 083 样图 1254×1254 正属此类，原生接口返回 accepted 只代表请求被接收。现已在缓存前把长边缩放到 500 像素，并让 `static_gif` 拒绝任一边超过 1000 像素的 GIF；公开精选 19 张已全部重建为 500 像素级单帧 GIF（合计约 1.4 MB，最大约 144 KB），旧的大尺寸缓存已删除。详见 [GIF 文件卡片修复](plans/2026-10-20-sticker-gif-file-fix.md)。

完整离线回归 284 项通过，覆盖素材索引与静态校验、单帧 GIF 缓存与缩放、选图/坏 ID/冷却、文字回执后才配图、图片回执与未知状态、跨重启冷却和撤销群隔离。公开索引已同步 19 张；真实 `run --check` 报告 `memesEnabled=true`、`memeAssets=19`、`memeNativeReady=true`，但真实群内图片发送尚未完成新尺寸下的现场确认，不能据此宣称表情显示已通过验收。
