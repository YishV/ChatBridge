# 本机通用文字聊天验收（2026-10-20）

用途已调整为通用微信群聊天。当前代码和主需求中已移除原先特定游戏的提示词、资料前置条件和资料字段。语音、唱歌尚未实现，按后续阶段推进。

## 已验证

- 用户在本机 `.env` 填入 DeepSeek 密钥，私有模型连通请求成功；密钥未输出或提交。
- `run --check` 通过：核心 `4.1.10.27`、本机回环接口、沙盘进程、已登录账号和唯一授权群匹配。
- `run --once` 启动后没有补答已有消息。
- 持续网关收到原生 `@` 后，模型生成文字并通过 native 发送。用户确认收到，匹配发出记录的服务器消息 ID 已确认。
- 未 `@` 的普通消息已验证自然接话；用户确认收到自然回复。服务器回执同样确认。普通消息的沉默分支也已观察到。
- 截至本次检查，聊天状态库共有 3 次确认投递，0 次待确认/未确认投递；后台日志无模型错误，标准错误日志为空。数字仅为本次验收快照。
- 66 项离线测试通过；覆盖匿名群上下文、隔离与过期、持久去重、冷却配额、动态暂停/撤销群、畸形模型响应、压缩/损坏提及元数据、加密数据库、游标、单实例锁、回执和发送状态未知。
- 审查发现的身份错误被吞和畸形模型响应异常均已修复：身份变化立即结束当前批次并停机；无效模型响应只使该条失败，不产生技术报错刷群。

## 参与规则

原生 `@` 直接回答。其他文本在频率允许时由模型判断是否接话；直接称呼机器人并提问或延续机器人上一条话题时优先接话，群友之间的普通闲聊可以沉默。自然决定使用 JSON 结构化输出，无效内容按沉默处理。

默认明确 `@` 冷却 5 秒、每群每小时最多 60 次模型调用。普通消息在最后一次发言约 5 秒后合并判断。每群上下文最多 20 条、10 分钟，仅内存保存；只有确认已发送的助手回复进入上下文。后台保持运行才能继续聊天，重启不补答历史。

## 自然接话与人设修复复验

用户反馈连续消息未获接话后，脱敏计数显示最后两次分别触发旧的 30 秒冷却与一次模型异常；旧日志不足以还原该次异常的具体 HTTP 状态或完成原因。经用户确认，现改为约 5 秒的连续发言合并，模型故障会记录固定分类代码，避免把故障混同于模型沉默。

更新后用户确认收到接话；后台记录先 `deferred` 等待，在没有新输入的轮询中完成 `naturalEvaluated`，取得一次 `confirmed` 发出回执，未出现模型错误或未确认发送。连续两条合并上下文的行为另有可控时钟回归覆盖。

独立人设文件 `config/persona.md` 已接入，保存后下一次请求读取；文件热更新、空/缺失/编码错误/超限、规则附加均通过测试。多群到期批次采用逐群生成后立即投递，首群致命错误阻止后续群推理。此轮完整回归 89 项通过。

## 拍一拍接入复验

原先网关仅接收文本，原生拍一拍被过滤。现已单独解析原生拍一拍事件，核对发起人、群和目标，只接受群友拍当前机器人；拍别人、自拍和手打文本不触发此分支。事件使用固定互动描述，不将拍一拍后缀传作提示词，也不伪装成原生 `@`。

用户确认收到按人设生成的文字回应；只读核对近期原生拍一拍与其稳定消息标识，匹配到两次 `confirmed` 投递及服务器消息 ID。较早、修复前的事件没有投递记录，不补发历史。

完整离线回归 105 项通过，包含严格 XML/压缩边界、目标校验、直接回应、限流/暂停/去重及取消自然待处理批次。审查另发现拍一拍初始服务器编号为 0 时会推进游标，已纳入等待逻辑，并以先失败后通过的两轮读取回归验证。更新后的持续后台已就绪，标准错误日志为空。

拍一拍仅触发文字回复，不执行拍回；沿用默认 5 秒冷却与每群每小时 60 次模型配额。连续密集拍动可能被限流。

## 成员区分与模型错误修复复验

收到自然接话 `model_response_invalid` 反馈后，确认原实现把响应 JSON 错误、结构异常和空内容合并显示，缺少进一步诊断，历史返回正文没有留存，无法断定该次具体形态。现已区分这些情况，默认单次超时 45 秒、输出 1200 token，可恢复失败最多重试一次，重试占用群配额；失败只留安全错误码与尝试次数，不会自动重发微信消息。

读取层已能区分授权群三位实际成员，均可读到微信昵称。新增稳定 API 成员名、当前说话人及历史助手回复归属，昵称相同不合并，改昵称和改人设不更换标识。联系人查询只取有效消息发送人的微信昵称，不取个人备注。生产标识密钥在本机保留，短期聊天内容仍不持久化。

完整回归 203 项通过，真实 DeepSeek 的两个虚构成员测试中，名字和偏好分别匹配；这不是实际微信群双成员验收。审查发现的 HTTP 协议异常漏接已修复。新版后台已启动；用户决定先使用、出现问题再反馈，本轮不再要求现场双成员验收，后续错误率继续观察。具体方案见 [修复记录](plans/2026-10-20-chat-reliability-and-members.md)。
